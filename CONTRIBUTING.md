# Contributing

Thanks for helping improve the PHES-ODM General Skill. The skill is mostly
prose — `SKILL.md` is instructions Claude reads at runtime — so "contributing"
here usually means changing what Claude is told to do, not changing code.

Questions and suggestions are also welcome on the PHES-ODM [discussion
board](https://odm.discourse.group) or in
[Issues](https://github.com/PHES-ODM/PHES-ODM-General-Skill/issues).

## Setting up

```console
git clone https://github.com/PHES-ODM/PHES-ODM-General-Skill.git
cd PHES-ODM-General-Skill
pip install pyyaml
```

To try your changes in Claude Code, symlink the skill directory so edits take
effect without re-copying:

```console
ln -s "$(pwd)/skills/phes-odm-general" ~/.claude/skills/phes-odm-general
```

Start a new Claude Code session after editing `SKILL.md` — the skill is read
when it is invoked, so an already-loaded copy will not reflect your edits.

Working on the skill is much easier with the
[phes-odm-search MCP](https://github.com/PHES-ODM/PHES-ODM-Search-MCP),
`odm-validate`, and `odm-map` installed; see the
[README](README.md#prerequisites).

## The one hard rule: never assert an ODM name you have not looked up

This repository's recurring defect has been *plausible but wrong* identifiers —
a table, column, or enumeration value that reads like real ODM and does not
exist. That failure is invisible to a reader and gets repeated downstream, so
every change that names a part of the data model must be checked against the
schema first:

- Look the name up with the phes-odm-search MCP, or find it in
  `skills/phes-odm-general/references/odm_v3.yaml` (and `odm_v2.yaml` if the
  claim is about v2).
- Remember that `required` and the allowed range are set **per table** in
  `slot_usage`. A column being required in `measures` says nothing about
  whether it is required in `samples`.
- Validate any example data with `odm-validate` before putting it in a
  document. Wide-format examples cannot be validated — say so where you use
  one.

Then run the checker, which enforces this mechanically:

```console
python scripts/check_skill_refs.py
```

It resolves every ODM identifier backticked in `SKILL.md` against the three
bundled schemas, verifies that each `class.slot` reference names a slot that
class really has, and checks that the skill frontmatter and both plugin
manifests agree on the skill's name and version. It runs on every push and pull
request.

If the checker flags a token that is not meant to be an ODM identifier — a new
CLI flag, a file name, a tool parameter — add it to `NON_ODM_TOKENS` in
`scripts/check_skill_refs.py` rather than loosening the identifier pattern.

## Editing SKILL.md

`SKILL.md` is a prompt, not documentation. A few conventions keep it working:

- **Frontmatter matters most.** The `description` is what Claude Code matches
  against a user's request to decide whether to load the skill. Keep the
  trigger phrases in it concrete and additive.
- **Keep it imperative.** "Call `get_class_slots` with that identifier" beats
  "the MCP can list slots".
- **Say what to do when a tool is missing**, rather than leaving Claude to
  guess at output it never saw.
- **Keep it short.** Everything in `SKILL.md` occupies context on every
  invocation. Detail that is only occasionally needed belongs in `references/`,
  which is read on demand.
- Wrap prose at 80 columns and keep the Markdown lint-clean
  (`.markdownlint.json` holds the rule set).

## Updating the bundled schemas

`skills/phes-odm-general/references/*.yaml` are generated by the [PHES-ODM
LinkMLGenerator](https://github.com/PHES-ODM/PHES-ODM-LinkMLGenerator) — do not
hand-edit them. To pick up a new ODM release, regenerate the schema, replace
the file, run `python scripts/check_skill_refs.py` to catch anything the
release renamed, and update the counts in
[`references/README.md`](skills/phes-odm-general/references/README.md).

## Reporting a problem you hit in real use

[`docs/PROBLEMS.md`](docs/PROBLEMS.md) tracks cases where the skill gave wrong
or misleading guidance in practice. It is the most valuable kind of
contribution: it records a failure that testing did not catch. Add an entry
describing what you asked, what the skill did, and what it should have done —
and, once it is fixed, note how.

## Pull requests

1. Branch from `main`.
2. Make the change, and update `CHANGELOG.md` under `[Unreleased]`.
3. Run `python scripts/check_skill_refs.py` and make sure it passes.
4. Describe in the PR what a user will now get that they did not get before.

Bumping the version means editing `.claude-plugin/plugin.json` and
`.claude-plugin/marketplace.json` together — the checker fails if they
disagree.
